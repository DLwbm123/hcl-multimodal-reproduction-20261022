## 坐标链的具体问题

部署transformers4.51.3的Qwen2VLImageProcessor，patch_size=14、merge_size=2，其smart_resize按28倍数调整尺寸。当前模型wrapper把原图送入processor，之后直接使用模型返回的像素值；schema canonicalizer仅改包装/键名，没有显式从processor坐标映射回原图。

CPU对一张实际输入做processor处理得到image_grid_thw=[1,40,44]，对应宽616、高560。该图原始宽626、高546；一个保存输出的y2=559超过原图546，但仍位于processor高560内。这是坐标契约风险的实证线索，不是通过标签反推坐标转换。

20个原图越界框中：

- 9个落在对应processor调整后图像范围内；
- 11个在原图和processor两种范围都越界。

因此，resize不对齐能解释部分输出的现象，但不能证明这9例全部采用processor坐标，更不能把其余11例也归入适配错误。还可能有模型过度延伸/不遵守边界等错误。**本次没有把坐标缩放、clip后重算IoU，也没有给出“修正后准确率”。**

## 公平性判断

两组由同一个worker启动，调用同一个AuditedModel/build_model、同一processor配置、同一个canonical_bbox和MedicalEvaluator，BF16/温度/输出预算相同，使用同一冻结的50个定位test IDs。差异在预先声明的H学习和memory状态，Static不学习。审计快照下两组组件版本均为0，模板状态相同；HCL后续可能按预注册门控更新组件，这是待比较的机制，不能要求学习后H仍等于Static。

**没有发现已发生的单侧评分放宽或一组独享坐标修正。** 但共同坐标契约不清会带来两种影响：

1. 两组的定位指标都混入坐标/输出服从能力，不能直接当作纯视觉定位能力。
2. HCL若改善“输出在边界内”的比例，收益可能主要来自接口服从；反之当前格式率必须1.0的门槛也可能拒绝有定位收益但仍越界的候选。B=0保留判定同样依赖成功谓词。不能把这种混杂解释成已经证明HCL机制强或弱。

另有一个已定位的脆弱条件：canonical_bbox仅在结构化question保留固定短语`output only one json object with bbox`时启用。Static50次转换均已验证成功触发；HCL定位阶段尚未完成，当前不能证明其后续改写下触发覆盖仍完全相同。这是需要用后续保存日志核对的接口耦合风险，**不是已发现HCL被偏袒的证据**。本轮不改此开关。
