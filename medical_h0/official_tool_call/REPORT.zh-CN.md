# Qwen2.5-VL 官方工具调用接口修复与验收

结论：已将自定义整段 JSON 响应协议替换为 Qwen-Agent 官方函数调用层，并对齐 **Qwen2.5-VL 的 Nous 协议**。正确协议下 43 次实际生成产生 43 次合法工具调用，未观察到非法 JSON 参数、schema 失败或未注册工具。但端到端 H0 验收仍未通过，未接入 HCL、未启动持续学习。

## 官方依据与版本纠正

- Qwen-Agent 固定提交 `31a4d36d123688581a9e9744427272b33ce940e0`，版本 0.0.34。
- [Qwen2.5-VL 官方 computer-use cookbook](https://github.com/QwenLM/Qwen2.5-VL/blob/3c4f939dda856110cefb315df6280b9b4eb15219/cookbooks/computer_use.ipynb) 对 `Qwen2.5-VL-7B-Instruct` 明确使用 `NousFnCallPrompt`；这是本次最终采用 Nous 协议的依据。
- [官方函数调用文档](https://qwen.readthedocs.io/en/v2.5/framework/function_call.html)说明模板与 SDK 在工具调用中的作用。不能将文本 Qwen2.5 文档单独视作 VL 的完整配置依据。
- 初次实现误选了官方 **Qwen2-VL 旧示例**中的 `qwen` 兼容协议。该轮 101 次生成全部保留；随后按具体 2.5-VL cookbook 纠正为 `nous`，没有按结果改医学提示、样本、工具、评分或门槛。两轮共用原始时间、144 次调用、500MB 上限；未重置预算。此前独立的手写 JSON 96 次失败运行也保持关闭。

## 改了什么

1. 工具 schema、assistant function call、function observation、继续生成与返回解析统一交给 Qwen-Agent `BaseFnCallModel`，配置 `fncall_prompt_type=nous`。最终协议为 `<tool_call>` / `<tool_response>`。
2. 本地代码仅实现受预算保护的 Transformers 生成及 LangChain 消息桥接，保留工具调用 ID / 名称对应检查。checkpoint 自身聊天模板不含工具 schema 逻辑，不能只传 `tools=` 就宣称原生工具支持。
3. 删除自定义 `{"tool_calls":...}` 整段响应契约及 `invalid_json_response` 假工具；不再追加括号修复提示、不补参数、不推测缺失的工具参数。官方 Nous 解析器支持 JSON5 / 部分调用提取，本地在执行前额外要求参数是对象、工具已注册且符合 schema；不能宣称它是约束解码或保证总能输出合法调用。
4. 未修改医学系统提示、受限工具内容/schema、官方 MedicalHarness LangGraph 规划流程和评分器。`read_facts`、受限算术 `calculate`、`submit_answer` 和官方 `update_plan` 保持相同。
5. 不启用 Qwen-Agent 的代码解释器、浏览器、shell 或网络工具。依旧是应用层能力限制，**不是 OS sandbox**。本次桥接只验收文本 MedTool，未验收图像工具路径。

## 冻结验收与结果

模型保持 Qwen2.5-VL-7B-Instruct BF16、greedy、单次最多 1024 输出 tokens、上下文上限 16384。MedicalHarness 固定 `8727186f04c25646e7ee1b9428f3b6dcd4239382`；planning on / context none / verification off。没有模型权重训练、HCL 候选优化、正式 32/107 benchmark 题目或答案访问。

13 项 CPU 协议/权限检查通过；6 个脚本驱动的真实 MedicalHarness 图执行通过，后者是 **0 模型调用的工程检查**。

真实模型的冻结门槛：6 例全部正确提交，均真正读取事实并执行算术；2 个首次 calculate 注入错误的用例均恢复；非法参数/工具调用数为 0。六例是两例旧开发失败、两例新合成数值及两例对应故障注入变体，不能当独立临床样本或泛化确认集。

| Nous 正确协议用例 | 实际模型生成数 | 结果 | 官方 utility |
|---|---:|---|---:|
| 旧 BMI | 5 | 正确提交 | 1.0 |
| 旧两步链 | 8 | ratio=4 正确，最终应为12，却提交36 | 0.5 |
| 新 BMI | 6 | 正确提交 | 1.0 |
| 新两步链 | 8 | ratio=3 正确，最终应为15，却提交75 | 0.5 |
| BMI 故障恢复 | 7 | 注入错误后重算得到25，但提交名 `compute_bmi` 无法匹配请求的BMI | 0.0 |
| 两步链故障恢复 | 9 | 已执行到最后规划；共享144调用用尽，提交未完成 | 未完成，不作完整准确率观察 |

实际正确协议生成合计43；最后一例记录10次 harness请求，其中第10次在预算检查处拒绝，**没有模型生成**。其 `provider_failure` 是上游对预算异常的归类，不是模型协议格式错误。保留六例完整验收分母，gate=false；已完成五例中两例完全正确，不把最后一例当完整负准确率样本。

官方评分器接受普通 `BMI` 缩写以及旧协议的 `BMI_Calculator`；不能把这两种名称误报为评分失败。实际名称错误发生在故障恢复用例的 `compute_bmi`。没有通过事后改别名或评分来使其过关。

兼容协议的对照记录：101 次生成，69 次合法/32 次非法工具调用，3/6端到端通过；三例链任务均到24轮上限。Nous 的43/43合法调用说明该固定样本中协议执行改善，**不证明任务准确率提高或未来调用一定合法**。

## 错误定位

多步链失败可直接定位到模型的计算计划，而非工具返回损坏：

- 旧链先调用 `(8 / 2) * 3`，工具返回12；模型随后再次调用 `12.0 * 3`，返回36，最终提交36。
- 新链先调用 `(21 / 7) * 5`，返回15；随后又调用 `15.0 * 5`，返回75，最终提交75。

工具按传入表达式正确计算，模型混淆了中间量与已完成的最终量。协议解析合法与数学依赖关系正确是不同门槛。注入错误后的重试也不等于最终提交正确。

## 成本、停止和 HCL 边界

本次总计144次实际生成=兼容协议101+Nous43；生成记录耗时约219.05秒（包含各次模型加载），输入tokens合计425,972，输出8,414。此前手写JSON96次单列，不能遗漏，也不能混入本轮144次预算。

父监督和worker均自然退出，结果退出码2表示验收失败。已核四个父/worker PID 均不存在；实际计量占用约102.50MB（含10MB预留），从准备起点到最后worker退出约537.53秒；未删除历史文件、未扩大原调用/时间/存储限制。

**不接HCL**：接口传输已改为官方实现，但多步依赖、答案契约和完整错误恢复尚未过关。后续需先验收这些H0行为；不能继续靠修改 JSON 提示宣称工具接口已全面可用。HCL之后只能更新已声明的流程/选择/记忆策略，不能更改工具权限、schema、评分或冻结答案契约。
